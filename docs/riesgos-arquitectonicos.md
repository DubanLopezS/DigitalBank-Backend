# Riesgos arquitectónicos

Los riesgos se sacaron del código de `main`. Lo marcado como "dato del equipo" viene de la configuración de Render o Supabase y no se puede ver en el repo.

| id | riesgo | causa o evidencia | probabilidad | impacto | mitigación actual o acción |
| --- | --- | --- | --- | --- | --- |
| R01 | Un cambio de esquema rompe otra API | Las tres APIs usan la misma base y solo `core-api` tiene migraciones (ADR-0009). `auth-api` valida sus entidades al arrancar (`ddl-auto=validate`), pero `reportes-api` y `ClienteConsultaAdapter` de `core-api` usan SQL a mano que nada revisa hasta que se ejecuta (ADR-0011). | media | alto | Flyway solo en `core-api`. Acción: antes de cada migración revisar qué columnas usan `auth-api` y `reportes-api`, y actualizar `reportes-api/src/test/resources/sql/esquema-movimientos.sql`. |
| R02 | Orden de arranque | Solo `core-api` aplica migraciones, y con Auto-Deploy las tres se reinician con el mismo merge (dato del equipo). Si `auth-api` arranca primero y le falta una tabla o columna, se cae; `reportes-api` arranca igual, pero sus consultas fallarían (ADR-0009). | media | medio | En el primer despliegue arranca `core-api` primero. Acción: cuando un merge traiga una migración, confirmar que `core-api` terminó de arrancar y reiniciar después las otras dos. |
| R03 | Un token no se puede revocar antes de que venza | `JwtAuthenticationFilter` solo revisa firma y vencimiento, y el token dura 60 minutos (`security.jwt.expiration-minutes` en `auth-api`). Un usuario bloqueado, un cliente INACTIVO o alguien a quien le cambiaron el rol sigue operando hasta que vence. `RetiroServiceImpl` y `TransferenciaServiceImpl` no revisan el estado del cliente (ADR-0010). | media | medio | Token de 60 minutos; el estado de la cuenta se lee de la base en cada operación. Acción: revisar el estado del cliente en las operaciones que mueven dinero. |
| R04 | Cualquier API con el `JWT_SECRET` puede firmar tokens | Las tres `JwtServiceImpl` arman la clave con `Keys.hmacShaKeyFor` a partir del mismo secreto (ADR-0010). Con el secreto de cualquiera de los tres servicios se puede firmar un token de ADMIN. | baja | alto | El secreto está solo en las variables de Render (dato del equipo). Acción: firma asimétrica, con la clave privada solo en `auth-api`. |
| R05 | Ninguna separación de privilegios en la base | Las tres APIs se conectan con `DB_USERNAME` y `DB_PASSWORD`; que sea el mismo usuario en las tres es dato del equipo. Que `reportes-api` y `ClienteConsultaAdapter` solo lean depende solo del código. El ADR-0009 lo deja como mejora. | baja | alto | Ninguna en la base. Acción: un usuario de solo lectura para `reportes-api`. |
| R06 | Seguridad y JWT duplicados entre APIs | Siete clases con el mismo paquete y nombre (ADR-0009). Las copias ya se separaron: el mensaje del 403 de `auth-api` es otro, `core-api` deja pasar `/api/auth/login` sin tener ese endpoint, solo `reportes-api` pone `UTF-8` en el 401 y el 403, y el filtro de `auth-api` no guarda el `clienteId`. | alta | medio | Ninguna. Acción: revisar todas las copias en cada cambio. |
| R07 | Deadlock en transferencias cruzadas | Dos transferencias entre las mismas cuentas en sentido contrario bloquean dos filas cada una (ADR-0007). Depósito y retiro bloquean una sola fila. | baja | medio | `bloquearEnOrden` de `CuentaServiceImpl` bloquea siempre primero el id menor, y `CuentaServiceImplTest` verifica el orden. Ningún test lo cubre contra Postgres real (R16). |
| R08 | Una transferencia queda con una sola fila | El `CHECK` de la V3 revisa cada fila por separado, así que la base acepta una fila de transferencia sin su pareja (ADR-0008). | baja | medio | `TransferenciaServiceImpl` guarda las dos filas en el mismo `@Transactional`; lo verifican `TransferenciaServiceImplTest` y `CuentaServiceImplIntegrationTest`. Queda expuesto a inserts hechos a mano en la base. |
| R09 | Se agotan las conexiones a Supabase | Dato del equipo: el pooler en modo sesión permite 15 conexiones, y con el pool por defecto de 10 por API el historial dio 500 con `EMAXCONNSESSION`. Ahora cada API tiene máximo 3 (ADR-0012). En el repo no hay configuración de Hikari. | media | alto | Variables `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=3` y `SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE=1` en los tres servicios (dato del equipo). Acción: poner esos valores en los `application.properties` con una variable de entorno, y recalcular si se agrega una instancia o una API. |
| R10 | Render free apaga las APIs | Dato del equipo: tras 15 minutos sin tráfico el servicio se apaga y tarda de 3 a 5 minutos en volver. Cada API se apaga por separado. | alta | medio | Ninguna. Acción: despertar las tres APIs unos minutos antes de una demo. |
| R11 | Auto-Deploy reinicia las APIs en cada merge | Dato del equipo: cada merge a `main` dispara un despliegue en Render. Si Render espera a que pase el CI antes de desplegar es dato del equipo. | alta | medio | El CI (`.github/workflows/ci.yml`) corre los tests y SonarCloud en cada PR, y los Dockerfile corren los tests al construir. Acción: no hacer merge cerca de una demo; ver R02. |
| R12 | Swagger abierto en producción | Las tres APIs tienen `springdoc-openapi-starter-webmvc-ui` en su `pom.xml`, ningún `application.properties` lo apaga y las tres `SecurityConfig` dejan `/swagger-ui/**` y `/v3/api-docs/**` sin token. Cualquiera ve la lista completa de endpoints. | alta | bajo | Los endpoints siguen pidiendo token. Acción: `SPRINGDOC_APIDOCS_ENABLED=false` y `SPRINGDOC_SWAGGERUI_ENABLED=false` en Render; ningún test los cubre. |
| R13 | Supabase sin RLS | Ninguna migración activa Row Level Security. Si la API REST de Supabase está habilitada para este proyecto es dato del equipo. | baja | alto | Ninguna. Acción: confirmar en Supabase si esa API está activa; si lo está, apagarla o activar RLS en las tablas. |
| R14 | Contenedores corren como root | Los tres Dockerfile no tienen `USER`, y la imagen `eclipse-temurin:21-jre` corre como root si no se cambia. | baja | medio | Ninguna. Acción: crear un usuario sin privilegios y agregar `USER` en la etapa final. |
| R15 | Los 401 y 403 no llevan timestamp | Los manejadores de `SecurityConfig` escriben el JSON a mano sin `timestamp`, y `GlobalExceptionHandler` sí lo pone. Un 403 de `@PreAuthorize` y un 403 de `AccesoNoAutorizadoException` llegan con formato distinto, y en `auth-api` el mensaje también cambia. | alta | bajo | Ninguna. Acción: usar el mismo cuerpo en los dos casos. |
| R16 | Los tests no ejercitan los CHECK ni los bloqueos de Postgres | En `auth-api` y `core-api` los tests usan H2 con Flyway apagado y `ddl-auto=create-drop`, sin los `CHECK` de las migraciones (por ejemplo `saldo_contable >= 0`, el de transferencias y el largo del motivo). Ningún test cubre el `FOR UPDATE` con Postgres (ADR-0007). `reportes-api` crea sus `CHECK` en H2 desde una copia manual del esquema. | media | medio | Las mismas reglas están también en los DTO y los servicios. Acción: tests de integración con Postgres real. |
| R17 | ADMIN y CAJERO solo se crean con un script SQL | `CredencialesServiceImpl` solo crea usuarios CLIENTE y no hay endpoint para crear ADMIN ni CAJERO. `POST /api/clientes` exige ADMIN y los depósitos exigen ADMIN o CAJERO, así que en una base nueva nadie puede registrar clientes hasta correr el script. | media | alto | `docs/scripts/crear-usuarios-internos.sql`, que no duplica si se corre dos veces (`ON CONFLICT DO NOTHING`). Acción: dejar el paso escrito en el README, que hoy solo tiene el título. |
| R18 | `CuentaServiceImpl` e `ICuentaService` con varias responsabilidades | `ICuentaService` tiene 9 métodos: abrir cuenta, acreditar, debitar, validar titularidad, dos búsquedas por número, bloquear en orden y dos consultas de estado. El ADR-0006 ya lo advertía. | alta | medio | Ninguna. Acción: separar la apertura de cuenta de los movimientos de saldo. |
| R20 | Endpoints sin `@PreAuthorize` | `POST /api/cuentas`, `/retiros` y `/transferencias` quedan solo para CLIENTE porque los tokens de ADMIN y CAJERO no traen `clienteId` y la validación de titularidad responde 403. Saldo e historial deciden el permiso dentro del servicio. Si cambia esa validación, el endpoint queda abierto a otros roles sin que nada lo avise. | media | alto | `CuentaServiceImplIntegrationTest` verifica el 403 con `clienteId` nulo. Acción: poner el rol explícito con `@PreAuthorize`. |
| R24 | Errores que no son `ApiException` terminan en 500 | `GlobalExceptionHandler` solo maneja `ApiException`, `MethodArgumentNotValidException` y `HttpMessageNotReadableException`. Los errores de base que sí pueden llegar terminarían en 500: pool agotado, deadlock o espera de bloqueo, y la violación de `UNIQUE` cuando dos registros con el mismo correo o documento llegan a la vez, porque `ClienteServiceImpl` revisa antes de insertar. | media | medio | Ninguna. Acción: manejar `DataIntegrityViolationException` como 409 y los errores de conexión con una respuesta propia. |
| R25 | El bloqueo del login sirve para bloquear a otro y para saber qué correos existen | `Usuario` bloquea la cuenta una hora después de 3 intentos fallidos, así que cualquiera que sepa un correo lo puede bloquear. Con un correo que no existe `AuthServiceImpl` responde siempre 401; con uno que existe, el cuarto intento responde 429. | media | medio | Ninguna. Acción: responder igual en los dos casos. |
| R26 | El monto de apertura no aparece en el historial | `CuentaServiceImpl.abrirCuenta` guarda la cuenta con el monto de apertura como saldo inicial pero no registra ninguna `Transaccion`. La HU-05 solo pide que la cuenta inicie con ese monto (criterios 1 y 4), así que se cumple, pero en el historial el `saldoAnterior` del primer movimiento no es 0 y no hay movimiento que lo explique. | alta | bajo | Ninguna. Acción: si se quiere que el historial lo muestre, registrar una `Transaccion` al abrir una cuenta con monto. |
| R27 | SQL en los logs de producción | `auth-api` y `core-api` tienen `spring.jpa.show-sql=true` y `format_sql=true` en `src/main/resources/application.properties`, así que cada consulta sale en los logs de la API. | alta | bajo | Ninguna. Acción: `SPRING_JPA_SHOW_SQL=false` en Render. |

Sobre R24: no encontramos forma de disparar por HTTP las otras excepciones que lanza el código: la `IllegalArgumentException` de `CuentaServiceImpl.validarMonto` (los DTO validan el monto antes), la `IllegalStateException` de `GeneradorNumeroCuenta` (25 números repetidos seguidos) y el `orElseThrow()` de `obtenerRol` (el filtro siempre pone un rol).

## Deuda técnica

Estos son problemas de calidad del código que no cambian la arquitectura.

| id | riesgo | causa o evidencia | probabilidad | impacto | mitigación actual o acción |
| --- | --- | --- | --- | --- | --- |
| R19 | Autorización por rol con roles escritos como texto | `SaldoServiceImpl` y `MovimientoServiceImpl` comparan el rol con `"ADMIN"` y `"CAJERO"`, y `SaldoController` y `MovimientoController` le quitan `"ROLE_"` a mano. `core-api` y `reportes-api` no tienen el enum `Rol`. | media | medio | Tests de servicio con cada rol. Acción: un enum o constantes compartidas para los roles. |
| R21 | La regla de saldo disponible está repetida en 3 sitios | `Cuenta.getSaldoDisponible()`, `SaldoServiceImpl.consultarSaldo` y `CuentaResponse.from` restan la retención cada uno por su lado. | baja | medio | Hoy ningún código cambia `retencion`, así que siempre es 0. Acción: usar `getSaldoDisponible()` en los tres. |
| R22 | La identidad se saca de `Authentication` en cada controller | 7 copias en `core-api` (`CuentaController` 1, `EstadoCuentaController` 3, `SaldoController` 1, `RetiroController` 1, `TransferenciaController` 1) y 1 en `MovimientoController` de `reportes-api`, con casts como `(UUID) authentication.getDetails()` o `UUID.fromString(authentication.getName())`. `obtenerRol` está copiado en `SaldoController` y `MovimientoController`. | media | bajo | Ninguna. Acción: sacarlo a un solo lugar por API. |
| R23 | Código sin uso | Sin consumidor en producción: `IUsuarioQueryService` y `UsuarioQueryServiceImpl`; `obtenerResumenPorDocumento` de `IClienteService` y el `ClienteResumenResponse` de `auth-api`; `obtenerIdPorNumero` de `ICuentaService`; `getExpirationMinutes` en el `IJwtService` de `core-api`; el `permitAll` de `/api/auth/login` en `core-api`; y `security.jwt.expiration-minutes` en el `application.properties` de `reportes-api`, que nadie lee. | baja | bajo | Ninguna. Acción: borrarlo junto con sus tests. |
